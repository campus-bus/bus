# 路段运行时间预估方法

> 版本：v1.0 | 基于 2026-06-12 ~ 2026-06-20 的 21 条实测记录推算  
> 更新：有新实测数据后，重新执行本文档中的步骤即可

---

## 一、数据来源

| 来源 | 说明 |
|---|---|
| Supabase `measurements` 表 | 用户实测的上车→下车段耗时（GPS 自动记录或手动计时） |
| `public/data/route_params.json` | 当前各路线站间秒数配置 |
| `public/data/route_paths.json` | 各路线路径经纬度坐标 |
| `public/data/route_stops.json` | 各路线站点经纬度坐标 |

## 二、路线分类

| 车型 | 路线 | RouteKey |
|---|---|---|
| **公交** | 环线1路 | HX1_NORMAL |
| **公交** | 就餐专线 | HX1_DINING |
| **接驳车** | 环线2路 | HX2_NORMAL |
| **接驳车** | 环线3路（研究生宿舍楼发车） | HX3_NORMAL |

## 三、站名修正

从数据库中读取实测记录时，需先修正历史站名：

| 旧名 | 新名 | 适用范围 |
|---|---|---|
| 高超楼 | 系统楼 | 环线1路、就餐专线 |
| 高超楼（作为始发站） | 系统楼 | 环线3路（HX3_GAOCHAO，即第一段的 from） |
| 教勤连 | 网球场 | 所有路线 |

> 环线3路上的「高超楼」和「系统楼」是**两个独立的站点**（均在 HX3_NORMAL / HX3_GAOCHAO 路线上），不要混淆。

## 四、预估值计算方法

### 步骤 1：按 (路段, routeKey) 分组

从 Supabase 拉取全部 `measurements` 记录，按路线修正站名后，以 `routeKey` 为维度分组。

例如：
```
HX1_NORMAL:
  研究生宿舍楼→东门: [65, 71, 88]
  东门→2号宿舍楼: [59, 72, 73, 88]
  ...

HX3_NORMAL:
  研究生宿舍楼→一食堂: [70, 70, 73, 91, 110, 10]
  ...
```

### 步骤 2：按样本量计算

| 样本量 N | 方法 |
|---|---|
| N ≥ 5 | 排序后去掉最小值、最大值，剩余取**均值** |
| 1 ≤ N ≤ 4 | 直接取**均值** |
| N = 0 | 无实测，进入步骤 3 查找参照 |

> 例：`研究生宿舍楼→一食堂` 实测 `[10, 70, 70, 73, 91, 110]`  
> → 排序 `[10, 70, 70, 73, 91, 110]`  
> → 去头尾 `[70, 70, 73, 91]`  
> → 均值 **76s**

### 步骤 3：无实测段的参照查找（优先级从高到低）

```
1. 同车型 + 同路段 → 直接使用
   例：HX2_NORMAL「305教学楼→研究生宿舍楼」无实测 → 用 HX3_NORMAL 同段实测 78s

2. 跨车型 + 同路段 → 直接使用
   例：HX2_NORMAL「二食堂→5号宿舍楼」无实测 → 用 公交 同段实测 66s

3. 同路线的反向等同段 → 直接使用
   例：就餐专线「理学院→系统楼」无实测 → 用就餐自身「系统楼→理学院」45s

4. 其他路线的反向等同段 → 先取值，然后按倍率放大
   例：就餐专线「5号宿舍楼→二食堂北」无实测 → 用环1「二食堂→5号宿舍楼」66s → ×1.44 = 95s

5. 按路径实际距离和平均速度推算
   例：HX2 未测段 → 用已知段的总距离÷总时间得平均速度 4.3m/s → 推算未测段

6. 以上都没有 → 保持原预估不变，列入待实测清单
```

### 步骤 4：就餐专线倍率

就餐时段人流量大，车速慢、上下客时间长。需要单独计算倍率：

找出**同时在就餐专线和环线1路都有实测的段**，计算每段的倍率，取平均：

| 共同段 | 就餐实测 | HX1实测 | 倍率 |
|---|---|---|---|
| 系统楼→理学院 | 45s | 32s | ×1.41 |
| 理学院→二食堂 | 232s | 158s | ×1.47 |
| **平均** | | | **×1.44** |

就餐专线中，非自身反向的引用段，需要在基础值上 ×1.44：

- 自身反向段（如理学院→系统楼 = 系统楼→理学院）：**不乘倍率**，直接等同
- 引用其他路线段（如一食堂→305 = 环3 图书馆→305）：**×1.44**

### 步骤 5：环线3路 激光所→系统楼 距离比拆分

历史实测中「激光所→高超楼」实际覆盖了 激光所→高超楼→系统楼 两段（因为当时系统楼站尚未加入路线）。

根据站点经纬度计算直线距离：
- 激光所 → 高超楼：462m（79%）
- 高超楼 → 系统楼：123m（21%）

将实测总时间 133s 按距离比例拆分：
- 激光所→高超楼：133 × 79% = **105s**
- 高超楼→系统楼：133 × 21% = **28s**

HX3_GAOCHAO 各段与 HX3_NORMAL 保持一致。

### 步骤 6：环线2路 速度推算

已知 6 段的总距离 ÷ 总时间 = 平均速度：

| 已知段 | 距离 | 时间 | 速度 |
|---|---|---|---|
| 研究生→一食堂 | 224m | 76s | 2.9 m/s |
| 二食堂→5号 | 269m | 66s | 4.1 m/s |
| 5号→305 | 329m | 63s | 5.2 m/s |
| 305→研究生 | 261m | 78s | 3.4 m/s |
| 门诊部→1号 | 395m | 73s | 5.4 m/s |
| 1号→军体 | 280m | 57s | 4.9 m/s |
| **合计** | **1758m** | **413s** | **4.3 m/s (15.3 km/h)** |

用平均速度推算未测段：

| 未测段 | 距离 | 推算 |
|---|---|---|
| 一食堂→门诊部 | 231m | 231÷4.3 = **54s** |
| 军体→水上训练中心 | 260m | 260÷4.3 = **61s** |
| 水上→二食堂 | 247m | 247÷4.3 = **58s** |

### 步骤 7：写回 route_params.json 并重新生成预测

修改 `route_params.json` 中每个段的 `finalSegmentSeconds` 和 `cumulativeSeconds`，更新 `totalSeconds`。

然后运行：
```bash
node scripts/regenerate_predictions.js
```

这会根据新的 `route_params.json` 和 `departures.json` 重新生成 `arrival_predictions.json`（2282 条到站预测）。

## 七、后续更新流程

当有新的实测记录后，按以下步骤更新预估：

```bash
# 1. 从 Supabase 拉取全部 records
# 2. 按本文档第三节修正站名
# 3. 按第四节步骤1-6重新计算各段预估值
# 4. 写回 public/data/route_params.json
# 5. 重新生成 arrival_predictions
node scripts/regenerate_predictions.js

# 6. 构建部署
npm run deploy
```

**注意事项**：
- 公交（HX1/DINING）和接驳车（HX2/HX3）始终分开统计
- 就餐专线的倍率应每次重新计算（有新数据后比例可能变化）
- 新增记录后，之前靠速度推算或跨路线参照的段可能变为有实测，优先使用实测
- 站名修正规则如有变化，更新本文档第三节
