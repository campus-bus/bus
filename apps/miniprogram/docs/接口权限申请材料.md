# 微信小程序 · 地理位置接口权限申请材料

> 适用接口：`wx.getLocation`、`wx.startLocationUpdate`、`wx.onLocationChange`
> 申请入口：微信公众平台 → 开发 → 开发管理 → 接口设置 → 地理位置接口 → 申请
> 整理时间：2026-10-18

---

## 〇、申请前必须确认的两件事

1. **小程序类目**：位置接口只对特定类目开放。本小程序应选 **「工具」→「信息查询」**（个人主体可选，官方开放类目里明确写了"与地理位置相关的服务，比如……信息查询"）。
   - 若当前类目是"教育""生活服务"等未开放类目，**先改类目并通过审核**，否则接口一律驳回。
   - `wx.startLocationUpdate` 的开放类目更窄，同样只认「工具 → 天气 / 信息查询」。
2. **隐私保护指引**：在小程序后台「设置 → 服务内容声明 → 用户隐私保护指引」中，勾选并填写「位置信息」的用途说明（文案见第四节），否则真机调用会被拦截。

## 一、`wx.getLocation` 使用场景说明（提交文案）

**短版（约 190 字，直接粘贴）**

```
本小程序是校园环线班车时刻查询工具，核心功能是"根据用户当前位置，推荐步行可达的乘车点，并显示这些站点的下一班车到站时间"。
用户进入首页点击"获取附近站点"时调用 getLocation，用于：
1. 计算用户与校园内 20 个班车站点的直线距离，筛选 200 米内可达站点；
2. 在站点卡片上显示步行距离与步行耗时，帮助用户在发车前判断能否赶上。
位置信息仅在手机本地参与距离计算，不上传服务器、不存储、不用于广告或其他用途。不做定位时，用户可手动选择站点，功能仍可正常使用。
```

**长版（约 280 字，若后台字数放宽可用）**

```
本小程序为高校校园环线班车时刻查询工具，服务于校内师生在固定线路（环线1路、就餐专线、接驳1路、接驳2路）上的候车需求。校园面积较大，站点分散且相距数百米，用户需要知道自己离哪个乘车点最近、走到那里要多久，才能判断是否赶得上即将发车的那一班。
调用 getLocation 的具体场景：用户进入首页后点击"获取附近站点"，小程序读取一次当前位置，与内置的 20 个站点坐标逐一计算距离，把 200 米内的站点按距离排序展示，并给出"步行约 3 分钟""距你 120 米"等提示，同时列出这些站点的下一班车到站倒计时。
位置仅用于本地距离计算，不上传、不存储、不共享，不采集后台位置，不用于广告。拒绝授权时用户仍可手动搜索并选择站点，核心功能不受影响。
```

## 二、`wx.startLocationUpdate` + `wx.onLocationChange` 使用场景说明（提交文案）

> 两个接口建议**同一次提交**，文案一致，写清"前台持续定位"的必要性。

**短版（约 200 字，直接粘贴）**

```
本小程序的地图页需要持续显示"用户当前位置"与"校园班车实时位置"的相对关系，因此使用 startLocationUpdate + onLocationChange 在**小程序处于前台时**接收位置变化。
场景：用户在校园内步行前往车站途中打开地图页，蓝色定位点随步行实时移动，可直观看到自己与站点的距离、班车当前在哪一段路上，从而决定继续前往还是改去另一个站点。
仅在用户主动打开地图页时开启，离开该页面或小程序切到后台立即停止监听；不采集后台位置，不上传、不存储轨迹，位置数据不共享给第三方。
```

**长版（约 290 字）**

```
本小程序地图页的核心是"我在哪、车在哪"。校园环线为固定闭环线路，班车不停在站台等待，用户必须根据班车当前所处路段判断能否赶上，因此需要看见自己位置相对于路线、站点的实时变化，而不能只取一次坐标。
调用方式：用户主动点击进入"地图"页时调用 startLocationUpdate 开启前台定位，并通过 onLocationChange 每秒接收一次位置更新，绘制定位蓝点、刷新与各站点的距离；用户离开地图页或小程序进入后台时立即调用 stopLocationUpdate 并在 onUnload 中移除监听。
范围与合规：仅前台使用，未申请也未使用后台定位（requiredBackgroundModes 未配置 location）；坐标仅在本地渲染，不上传服务器、不写数据库、不生成轨迹、不共享第三方。拒绝授权时地图页仍可浏览线路与站点，仅不显示自身位置。
```

## 五、提交时的小技巧

1. **一次只申请一个接口**，`startLocationUpdate` 与 `onLocationChange` 绑定提交，`getLocation` 单独提交，驳回时便于定位问题。
2. `content` 字段（或后台"使用场景"输入框）**上限 300 字符**，务必用第一、二节的短版，超长会被截断。
3. 三个接口的理由**不要复制粘贴同一段**，审核会判定"重复机械提交"直接驳回。本文已按接口差异化撰写。
4. 若被驳回，常见理由与对策：
   - 「小程序内未含有相应使用场景」→ 补截图/录屏，并确认截图来自小程序而非 H5；
   - 「类目不符合」→ 改类目到 工具 → 信息查询；
   - 「使用场景描述过于笼统」→ 写清"哪个页面、哪次点击、算出什么、给用户什么结论"。
5. 代码侧必须同时满足：`app.json`/`manifest.json` 的 `requiredPrivateInfos` 已声明三个接口，`permission.scope.userLocation.desc` 已填写用途说明，否则审核阶段会被拦截。
